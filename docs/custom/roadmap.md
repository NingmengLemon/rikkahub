# 长期路线

本文件记方向、阶段划分与策略。具体定制的落点与当前状态见 [`README.md`](README.md) 的定制清单。

## 定位

`custom` 目前是上游的个人定制分支，同时保留着最终独立成单独应用的可能：改包名、自己的 CI、按自己需求迭代、对数据层动手。

是否真的走完这一步，取决于两件事的成本对比：继续跟随上游的合并成本，和维护独立分叉的成本。本文件的作用是让那个决定在某天变得可执行，而不是现在就预设答案。

真正不可逆的那一步是改包名，因为它让新版本与旧版本成为两个应用，迁移只能靠备份导出导入。因此所有前置准备都在为它服务。

当前处于阶段 0：继续按现有约束做定制，清单里尚未实施的项目等上游节奏放缓再做。阶段 1 的导入器是改包名与动数据层的前置，但它本身不依赖上游稳定性，可以随时开始。

## 阶段 1：易迁移

目标：官方客户端导出的备份，必须能导入本 fork。

为什么用导入器而不是「绝对不动存储结构」这种硬约束：区别在成本形态。硬约束是一次性的「不许动」，便宜，但把数据层封死；导入器是持续的「动了要维护一个转换器」，贵，但换来自由。这里选后者。

这笔自由不是无代价的。动了结构之后，升级会触发迁移，回退到旧版本会因为库的 schema 版本更高而无法打开。要用回退换数据层的自由，这一点得先认。

### 事实基础

官方备份是一个自包含 zip，不需要云端：

```
settings.json                        整个 Settings 的序列化，额外带 launchCount
rikka_hub.db                         VACUUM INTO 出来的标准 SQLite 快照
upload/ skills/ fonts/ media_creation/    附件，可选择不备份
```

`rikka_hub-wal` 与 `rikka_hub-shm` 也出现在官方恢复逻辑里，但当前版本导出时不产出这两个条目，恢复侧保留它们只是为了兼容更早的备份。

出口支持本地 SAF、WebDAV、S3 三种，三者共用 `data/sync/BackupManager.kt` 的同一套归档格式与恢复流程。

官方恢复的做法是「用当前 schema 直接打开备份里的旧库，靠 Room migration 链把版本升上来」（`BackupManager.kt` 的 `stageRestore`）。因此官方能跨版本恢复的原因是迁移链一直在。

### 设计要求

1. 独立只读层，不依赖 Room migration 链。

   现在 custom 与官方 3.0.0 发布版都是 v30 且 schema 一致，这条张力暂时不会出现。上游 master 已经是 v31（`Migration_30_31`），跟进之后我们也会是 v31。开始改结构之后就变了：`AppDatabaseFactory.create` 打开官方库，要么因为版本号更高而失败，要么在双方版本号相同、语义已经不同时静默读错。后者更危险，因为没有任何报错。

   所以导入器不能用我们自己的 `@Entity` 定义去解析官方库，必须以裸 SQL 读出来，转成领域模型，再写进我们自己的库。

   这一条只解决解耦方向，即我们的 schema 怎么演进都不影响读取官方库。它不等于可以随便改结构，我们自己的备份恢复仍要走自己的迁移链，见要求 6。

2. 官方 schema 在读取层里冻结。

   读取层自带一份官方 schema 的快照，不随我们的库演进。官方未来升到 v32，这里只改几条 SQL。

3. 单向转换，但自家数据必须有往返路径。

   我们新加的字段官方必然不认识，所以不追求我们的导出被官方客户端读回。

   但改包名的迁移是「旧版本导出、新版本导入」，旧版本可能是本 fork 的旧构建，它的库里已经带着我们自己的 schema 演进。所以导入侧必须同时接受两种来源：官方 schema 的库，和我们自己的历史 schema 的库。

   前者靠要求 1 的读取层，后者靠我们自己的 Room migration 链。

   两种来源必须先能分清。版本号靠不住，双方可能同号异义。Room 在 `room_master_table` 里为每个数据库保存了 schema 的 identity hash，可作判定依据；具体用什么判据由实现决定，但判定必须在读取任何业务表之前完成，判不出来就明确失败。

   这一条决定改包名时数据能不能搬过去，必须在阶段 1 内落地。

4. 导入时归档原始 zip。

   把官方产出的原始备份文件另存一份，永不删除。它本来就是官方自己产出的自包含文件，随时能被官方客户端吃回去。归档负责保命，转换器负责搬家，两者解耦之后改数据的胆子可以大很多。

5. `settings.json` 比数据库更麻烦，要单独设计。

   数据库是 SQLite，schema 好冻结。`settings.json` 是整个 `Settings` 数据类的序列化，这一个类横跨 provider 配置、assistant 模板、UI 主题、联网配置、备份配置和各种开关，`SettingsFields.kt` 把它拆成 DataStore key 的映射就有一百多行，上游自己也在用 `SettingsJsonMigrator` 在这个类上演进。这里同样需要一个「官方 Settings JSON 到我们的模型」的独立解析器，不能复用我们自己的反序列化。

6. 自家 schema 的演进仍要守住 migration 链。

   要求 3 的第二半依赖这一条。一旦我们的库改了结构，本 fork 旧构建产出的备份只能靠 `Migration_n_n+1` 升上来，所以动结构时必须同时写迁移，并且这个迁移要能被导入路径复用。

   这也是「不能随意回退」的来源。接受这条代价，才谈得上把数据层放开。

7. 读取层要校验官方 schema 版本。

   官方若做破坏性迁移（重建表、改字段语义），读取层读到的是语义不同的数据，静默转换会写坏我们的库。读取层要带已知版本的清单，遇到超出范围的版本明确失败，不做猜测。

### 验收

用归档的固定样本集跑，不靠肉眼抽查。样本分三类：

- 官方客户端导出的备份，至少覆盖多分支会话与重新生成、带附件与工具调用的消息、多 provider 与自定义 assistant、自定义主题与提示词
- 本 fork 旧构建导出的备份，用来验证要求 3 的往返路径
- 版本号超出已知范围的库，必须明确报错，不能靠猜

每次改动我们的 schema 或 `Settings` 结构之后重跑全部样本，比对导入后的条目数与关键字段。只编译通过不算数。

### 冻结的解除

阶段 1 完成之后，README 与 AGENTS.md 里对数据结构的冻结随之解除。完成指两件事都成立：导入器已实现，且在固定样本集上验证通过。

解除由一个已实现并验证的导入器触发，不是由时间或版本号触发。

### 与后续阶段的衔接

官方恢复走的是「启动前暂存，在 Koin、Room、SettingsStore 初始化之前替换文件」（`BackupManager.applyPendingRestore`）。这里可复用的是「启动前暂存、初始化之前落盘」这个时序，不是它的数据库路径：那条路径走 Room 迁移链，正是要求 1 要绕开的。

改包名之后是新装应用冷启动，在这个时序里插入转换步骤比在运行时导入更干净。

## 阶段 2：独立化

### 2.1 改包名

当前是 `me.rerere.rikkahub`，debug 变体带 `.debug` 后缀。

不受影响的部分：`FileProvider`、`DocumentsProvider`、`androidx-startup` 的 authorities 都是 `${applicationId}` 拼的，自动跟随。数据库文件名 `rikka_hub` 与 DataStore 文件名是不带包名的固定字符串，`rikka_hub.db` 是备份归档里的条目名，不是设备上的文件名。

真正的连锁反应有三条：

- 私有目录跟着包名走，改包名等于全新安装、零数据。因此阶段 1 必须先完成并验证通过，顺序不能反，反了就是把现有数据置于风险中
- 改包名后新旧两个应用并存，迁移路径只能是「旧应用导出、新应用导入」。旧应用可能是官方版，也可能是本 fork 的旧构建，两条来源都要能吃下，见要求 3
- `AndroidManifest.xml` 里的 `rikkahub://shortcut` scheme 是硬编码的，不跟包名走。两个应用都注册同一 scheme 时点快捷方式可能开错应用，需要换名

### 2.2 自己的 CI

这一步独立于阶段 1，可以随时提前做。

上游 `.github/workflows/daily-build.yml` 需要的前提：JDK 21（jetbrains distribution）、pnpm 11、Node 22、`submodules: recursive`、`web-ui` 先跑 `pnpm install --frozen-lockfile`。

三个 secrets 缺一不可：`KEY_BASE64`（keystore）、`SIGNING_CONFIG`（写进 `local.properties`）、`GOOGLE_SERVICES_JSON`。

`GOOGLE_SERVICES_JSON` 不能省。C2 只移除了 Firebase Analytics，Crashlytics 与 `google-services` 插件仍在，缺这个文件 `processReleaseGoogleServices` 会失败。

与本仓库的差异：不需要每晚发布 prerelease，不做发版，产物存为 workflow artifact 即可。

### 2.3 对数据层动手

前提是阶段 1 完成。第一批候选是拆掉 `Settings` 这个巨型类，因为它是数据层里收益最大、也最难维护的部分。

风险同样集中在这里：`Settings.kt`、`SettingsFields.kt`、`SettingsJsonMigrator` 和各设置页是上游改动最频繁的区域之一，拆它会显著抬高合并成本。

建议的时机与追更策略切换对齐：等 `app/` 的改动不再需要逐项对照上游之后，冲突压力本身就小了，那时再动。

## 追更策略

追更仍然要做。完全不跟的 fork 不会稳定在可用状态，它会慢慢烂掉：provider 协议变了、上游 API 挂了、崩溃修不上，最后连打开都用不了。

区别只在于跟什么、怎么跟。

### 模块边界

按模块切分，而不是按 commit 切分。

| 模块 | 性质 | 策略 |
| --- | --- | --- |
| `ai/` | provider SDK、协议适配、模型注册表，与 UI 重构解耦 | 尽量跟随上游 |
| `search/`、`document/`、`common/`、`highlight/` | 工具性质的独立模块 | 跟随上游 |
| `workspace/` | 沙箱文件系统与 shell 执行环境 | 跟随上游 |
| `web/` | Ktor 服务端与 web-ui 前端产物 | 跟随上游 |
| `material3/`、`ui/` | 主题工具与不依赖 app 逻辑的 Compose 组件 | 跟随上游 |
| `oauth/` | OAuth 授权与回调处理 | 跟随上游 |
| `app/` | UI、业务、Service，也是大部分定制的所在地 | 我们的地盘。上游的功能性改动逐项评估，bug 修复照跟 |
| `speech/` | C5 删掉了全部运行时实现，只留两个序列化类与它们的序列化测试 | 不跟随 |
| `mediagen/` | C1 保留模块以维持数据兼容，界面不使用 | 跟随，但改到 `MediaGenerationProviderSetting` 这类持久化类型时要复核 |

跟随 `ai/` 时要重放一处定制：C3 删掉了 `ai/util/Request.kt` 里给 aihubmix.com 加 `APP-Code` 请求头的分支。这是 `ai/` 下唯一一处定制，上游改这个文件时要重新删除。

`app/` 的上游功能不整体跟随。但在当前的整分支合并里，一旦在这里出现冲突，不逐行解：以上游版本为基线，重新应用定制清单登记的内容，顺手删掉不需要的上游新功能。C1 到 C7 的代码落点里，除 C3 的 `ai/` 一处与 C5 落在 `speech/` 的部分外，其余都在 `app/`；C4 另有仓库根的三份 README。逐行解冲突的成本远高于重放一遍。

取上游版本再重放这套做法只在整分支合并里成立。分层追更落地后不再整体 merge，`app/` 的处置变成：保命层改动手工摘，能力层评估后自己实现，地基层完全不动。两种做法以「是否还在整分支合并」为界，不混用。

上游 3.0.0 把多步生成循环搬进了 `ai/` 模块。下次同步时可以检验这个划分：如果 `ai/` 真的变成了可以独立跟随的干净依赖，说明边界成立；如果没有，就需要重新划分。

### 三层划分

保命层，必跟。provider 适配、上游 API breaking change、崩溃与安全修复。这类通常改动小、集中在 `ai/`，可以直接摘。

能力层，按需移植。上游新增的具体 feature 单独评估后自己实现，不要 cherry-pick，因为它们通常依赖同时期的 app 侧结构，摘过来会拖进来一串前置改动。

地基层，尽量不跟。架构重构、UI 大改。跟一次等于把定制全部重做一遍。上游 3.0.0 的三项重构就是这一类。

### 一次追更的动作

分层追更落地之后按下面的流程走。当前仍是整分支合并，见 README 的上游同步流程。

1. 扫跟随模块有没有保命层改动：

   ```powershell
   git log --oneline <上次同步点>..upstream/master -- `
     ai/ common/ document/ highlight/ material3/ mediagen/ `
     oauth/ search/ ui/ web/ workspace/
   ```

2. 列 `app/` 区间的提交，逐条标成 要 / 不要 / 以后再看：

   ```powershell
   git log --oneline <上次同步点>..upstream/master -- app/
   ```
3. 保命层直接摘；能力层记进定制清单，评估后自己实现；地基层跳过。
4. 跳过地基层时记下它动过哪些文件。后续保命层的改动很可能落在这批文件上，届时摘取成本会比平时高，需要单独判断，而不是直接 cherry-pick。
5. 跑测试，判据是没有新增失败。

### 定制原则的适用范围

README 里「改动尽量小，优先断入口」与「避开上游热区」这两条，目的只有一个：让上游的改动能廉价地合并进来。

它们不是本仓库的长期规矩，只是一笔合并成本的对价。等 `app/` 不再需要整体跟随上游（追更策略转向之后，或阶段 2 完成），`app/` 里的改动不再需要替上游让路，两条都可以放开：

- 在 `app/` 里，该删的实现直接删掉，不必为了可合并性留一整段死代码
- `ChatVM.kt`、`ChatService.kt` 这类高频文件可以随手改，不必专门绕开

`ai/` 那种仍要尽量跟随上游的模块不在此列，C3 的删除每次合并都要重放，「改动尽量小」在那里仍然划算。

同类的合并成本让步还有两处：把删掉的文件路径记进定制清单以便合并时逐项核对，以及新定制避开上游重构期（C6 与 C7 的暂缓就是这个原因）。这些同样只在整分支合并期间必要。

在这之前它们全都有效，因为合并成本是实打实的。

## 分发与合规

独立化有一个决策变量是要不要把这个 fork 分发给别人，它直接影响合规义务。

本仓库是 AGPL-3.0，而项目带 `web` 模块，能在设备上跑 Ktor 对外提供 Web UI。自己构建自己安装不构成分发，没有额外义务。但如果 APK 要分发出去，或者把 web 版挂到公网提供服务，就需要按 AGPL 提供源码。

改包名不改变这一条，它只是让「这是谁的修改版」这个问题变得明确。
