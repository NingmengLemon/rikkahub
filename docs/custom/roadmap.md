# 长期路线

本文件记方向、阶段划分与策略。具体定制的落点见 [`checklist.md`](checklist.md)，数据层的现状见 [`backup/README.md`](backup/README.md)。

## 定位

`custom` 目前是上游的个人定制分支，同时保留着最终独立成单独应用的可能：自己的 CI、按自己需求迭代、对数据层动手、独立分发。

是否真的走完这一步，取决于两件事的成本对比：继续跟随上游的合并成本，和维护独立分叉的成本。本文件的作用是让那个决定在某天变得可执行，而不是现在就预设答案。

真正不可逆的那一步是改包名，因为它让新版本与旧版本成为两个应用，迁移只能靠备份导出导入。包名已经改了（见阶段 2.1），所以现在只剩继续跟随与独立分叉之间的取舍。

当前的位置：阶段 2.1 的包名与构建侧改造已完成，阶段 1 的导入器也已落地并验收（C20 到 C26），数据结构的冻结随之解除。阶段 1 还剩 settings 形状校验；官方兼容导出的裁剪逻辑要等双方结构分叉时才有内容可做。导入器加迁移链已经能给整个数据层兜底，因此数据层改造不再有前置阻塞。

## 阶段 1：易迁移

目标：官方客户端导出的备份，必须能导入本 fork。

现状：导入器已落地并验收（C20 到 C26），官方客户端导出的备份能导入本 fork。分叉之前真实官方备份走的仍是 `stageRestore`，导入器要到我们改结构之后才被触发。

为什么用导入器而不是「绝对不动存储结构」这种硬约束：区别在成本形态。硬约束是一次性的「不许动」，便宜，但把数据层封死；导入器是持续的「动了要维护一个转换器」，贵，但换来自由。这里选后者。

这笔自由不是无代价的。动了结构之后，升级会触发迁移，回退到旧版本会因为库的 schema 版本更高而无法打开。要用回退换数据层的自由，这一点得先认。

备份的归档格式、恢复流程与分流判据在 [`backup/README.md`](backup/README.md)，转换路径在 [`backup/importer.md`](backup/importer.md)。

### 设计要求

八条约束数据层怎么改。前两条解决「读官方库不依赖我们的 schema」，第三条解决「两种来源要分清」，后几条解决自家数据与官方兼容导出。

1. 独立只读层，不依赖 Room migration 链。

   截至上游 3.1.1，custom 与官方发布版同为 v32 且 schema 一致（31 到 32 是 `AppDatabase` 里的 `AutoMigration`，`workspaces` 表加 `type` 与 `ssh_config`），这条张力暂时不出现。开始改结构之后就变了：`AppDatabaseFactory.create` 打开官方库，要么因为版本号更高而失败，要么在双方版本号相同、语义已经不同时静默读错。后者更危险，因为没有任何报错。

   所以导入器不能用我们自己的 `@Entity` 定义去解析官方库，必须以裸 SQL 读出来，再写进我们自己的库。写入选行级照抄而不是先转领域模型：JSON 字段原样搬运能保住未知字段，也避开了再序列化带来的格式漂移。

   这一条只解决解耦方向，即我们的 schema 怎么演进都不影响读取官方库。它不等于可以随便改结构，我们自己的备份恢复仍要走自己的迁移链，见要求 6。

2. 官方 schema 在读取层里冻结。

   读取层自带一份官方 schema 的快照，不随我们的库演进。快照停在官方 v32，官方日后再升版时加一份新快照。

3. 单向转换，但自家数据必须有往返路径。

   我们新加的字段官方必然不认识。要求 8 说的「导出能被官方读回」指的是在导出侧把官方不认识的表与列裁掉，不是让官方理解我们的新增字段。

   但改包名的迁移是「旧版本导出、新版本导入」，旧版本可能是本 fork 的旧构建，它的库里已经带着我们自己的 schema 演进。所以导入侧必须同时接受两种来源：官方 schema 的库靠读取层，我们自己的历史 schema 的库靠迁移链。

   两种来源必须先能分清。版本号靠不住，双方可能同号异义。Room 在 `room_master_table` 里为每个数据库保存了 schema 的 identity hash，可作判定依据；判定必须在读取任何业务表之前完成，判不出来就明确失败。

4. 导入时归档原始 zip。

   把官方产出的原始备份另存一份，永不删除。它本来就是官方自己产出的自包含文件，随时能被官方客户端吃回去。归档负责保命，转换器负责搬家，两者解耦之后改数据的胆子可以大很多。

   归档做在本地导入与 WebDAV 导入共用的 `restoreFromBackupFile` 里，在 `stageRestore` 成功之后执行，放 `noBackupFilesDir` 而不是 `filesDir`（后者整个目录被 web 路由暴露）。

5. `settings.json` 比数据库更麻烦，要单独设计。

   数据库是 SQLite，schema 好冻结。`settings.json` 是整个 `Settings` 数据类的序列化，这一个类横跨 provider 配置、assistant 模板、UI 主题、联网配置、备份配置和各种开关，`SettingsFields.kt` 把它拆成 DataStore key 的映射就有一百多行，上游自己也在用 `SettingsJsonMigrator` 在这个类上演进。这里同样需要一个「官方 Settings JSON 到我们的模型」的独立解析器，不能复用我们自己的反序列化。

   尚未落地的是形状校验：直接检查原始 JSON 的 key 与类型，包含嵌套对象的形状，转换仍复用现有反序列化。完整的冻结解析器与字段映射跟第一次改 `Settings` 结构一起做。

6. 自家 schema 的演进仍要守住 migration 链。

   要求 3 的第二半依赖这一条。一旦我们的库改了结构，本 fork 旧构建产出的备份只能靠 `Migration_n_n+1` 升上来，所以动结构时必须同时写迁移，并且这个迁移要能被导入路径复用。

   这也是「不能随意回退」的来源。接受这条代价，才谈得上把数据层放开。

7. 读取层要校验官方 schema 版本。

   官方若做破坏性迁移（重建表、改字段语义），读取层读到的是语义不同的数据，静默转换会写坏我们的库。读取层带已知版本的清单，遇到超出范围的版本明确失败，不做猜测。

8. 能导出官方客户端读得回去的备份，与自家导出并列。

   这是要求 1 的对称面，也是「改了结构就回不去」的解药。它在备份页上是第二个出口，不是把现有导出改掉：自家的导出始终带全量数据，包括我们新增的表与字段；官方兼容的导出只带官方认识的部分。

   当前两个出口的产物几乎一样：双方 schema 都是 v32，附件目录也一致，官方兼容出口在这一步只是把库原样带出去，分叉时会直接失败。也就是说现在把自家导出的 zip 直接交给官方客户端也能恢复。一旦我们改动结构，这个出口就必须真的裁：把官方不认识的表与列裁掉，并把 `user_version` 与 `room_master_table` 里的 identity hash 改回官方值。

   `settings.json` 不需要裁字段：官方恢复用的 `JsonInstant` 开着 `ignoreUnknownKeys`，多余字段会被忽略，归档里的 `launchCount` 就是先例。这个容忍度只覆盖不认识的 key，改已有字段的含义它救不了。

   裁剪逻辑和导入侧一样，要能在一份固定样本集上验证，判据是官方客户端恢复成功，且恢复后的会话条数与关键字段对得上。

### 验收

见 [`backup/acceptance.md`](backup/acceptance.md)。样本分五类，判据是「没有独立期望值就不算验过」，只编译通过不算数。

### 冻结的解除

冻结已解除，条件是导入器已实现并在固定样本集上验证通过。解除之后，数据层的门禁从「不许动」换成「动了要维护」：改 Room 结构要同时写迁移，改完要重跑验收样本；改已有字段的含义要先建写入侧的字段映射表，那是唯一能发现语义漂移的环节。仍然生效的约束列在 [`README.md`](README.md) 的「数据结构」一节。

官方兼容导出（要求 8）与这次解除直接相连：双方结构分叉之后，那个出口会直接失败，直到裁剪逻辑落地。

### 与后续阶段的衔接

官方恢复走的是「启动前暂存，在 Koin、Room、SettingsStore 初始化之前替换文件」（`BackupManager.applyPendingRestore`）。这里可复用的是「启动前暂存、初始化之前落盘」这个时序，不是它的数据库路径：那条路径走 Room 迁移链，正是要求 1 要绕开的。

改包名之后是新装应用冷启动，在这个时序里插入转换步骤比在运行时导入更干净。

## 阶段 2：独立化

### 2.1 改包名

已完成：`applicationId` 是 `top.lemoneko.rakkihub`，debug 变体带 `.debug` 后缀；`namespace` 仍是 `me.rerere.rikkahub`，类名与 R 类不受影响。

不受影响的部分：`FileProvider`、`DocumentsProvider`、`androidx-startup` 的 authorities 都是 `${applicationId}` 拼的，自动跟随。数据库文件名 `rikka_hub` 与 DataStore 文件名是不带包名的固定字符串，`rikka_hub.db` 是备份归档里的条目名，不是设备上的文件名。

真正的连锁反应有三条：

- 私有目录跟着包名走，改包名等于全新安装、零数据。把旧包数据搬过来只能走备份导出导入：结构相同的库走迁移链，结构与官方不同时走导入器
- 改包名后新旧两个应用并存，迁移路径只能是「旧应用导出、新应用导入」。旧应用可能是官方版，也可能是本 fork 的旧构建，两条来源都要能吃下，见要求 3
- `AndroidManifest.xml` 里的 shortcut scheme 是硬编码的，不跟包名走。两个应用都注册同一 scheme 时，外部隐式 intent 会落到不确定的那个，所以本分支用 `rakkihub://shortcut`，`res/xml/shortcuts.xml` 里的 `android:data` 与之对应

### 2.2 自己的 CI

这一步不依赖其它阶段，可以随时做。

`.github/workflows/daily-build.yml` 沿用上游，它的前提是：JDK 21（jetbrains distribution）、pnpm 11、Node 22、`submodules: recursive`、`web-ui` 先跑 `pnpm install --frozen-lockfile`。

两个 secrets 缺一不可：`KEY_BASE64`（keystore）与 `SIGNING_CONFIG`（写进 `local.properties`）。`GOOGLE_SERVICES_JSON` 不需要，本分支已按 C13 移除 Firebase 与 `google-services` 插件。

本仓库沿用上游的 nightly prerelease：固定 tag `nightly`，每天覆盖同一个 Release，附带分 ABI 的 APK 与 `mapping.txt`。不做正式版本发布。

### 2.3 对数据层动手

前提是阶段 1 完成，现在已具备。第一批候选是拆掉 `Settings` 这个巨型类，因为它是数据层里收益最大、也最难维护的部分。

另有一项导出侧的改造：备份导出可选包含工作区文件，默认不包括。工作区里是 PRoot 根文件系统与用户文件，体积大、多数不需要跟着备份走，所以默认排除，只在用户明确勾选时打包。它涉及导出流程的分支与体积提示，放在导入器稳定之后再动。

另一项候选是附件按内容 hash 去重：同一内容只留一份。做法是把文件名从随机 UUID 换成内容指纹，写之前先看目标在不在，在就复用。引用形式完全不变（还是绝对 `file://` 路径），所以消费方一处都不用动，序列化格式与 Room schema 也不变；指纹就在文件名里，文件名本身就是指纹，清理时不必再算一遍内容。

这件事的收益在真实备份上验证过：同一份内容被反复存了多份，去重后绝大部分体积可以回收。成因很直接：文件名是随机 UUID，写之前无从判断内容是否已经存在，于是同一张图在多个会话、多条消息里各存一份。

代价是删除语义要改：现在删消息会直接删文件（`ChatService.deleteUnreferencedFiles` 只保住上一次落库后仍被引用、以及队列与提交中消息引用的文件），同一份文件被多处引用之后这么做会把别处弄坏。所以去重之后删除只能摘登记，文件回收交给标记-清除。这一项还没落地，前提是先让草稿与待发送队列的附件引用进库：全量扫描读的是库，那两处的引用只在内存里，扫描覆盖不到，扫一遍就会误删。

去重要解决的是「同样的内容存多份」，还有一件独立的事是「引用绑死了安装路径」。后者不是去重的前提，但同样要改：现在是 `file:///data/user/0/<包名>/files/upload/...`，包名与用户号都在路径里，改包名、多用户、工作资料、换设备都会让引用整体失效（导入官方备份到改过包名的应用时，消息里的附件引用、助手头像与用户头像会同时断掉）。它还会挡住官方兼容导出：把库交给官方客户端时，里面存的仍是我们的绝对路径。改法是存相对形式、读取时在一处统一解析，并保留对绝对路径的兼容以接住存量数据。导入器的路径重写要保留，因为官方备份进来的方向仍然是绝对路径。

去重之后还要清理没人引用的文件，这一步用标记-清除，不用引用计数，且手动触发。引用计数要在消息删除、分支切换、助手删除、导入覆盖每一处维护，漏一处就少算，少算的结果是误删用户文件；标记-清除只要求「扫描覆盖所有引用点」，漏一处的最坏后果是少收一点垃圾。扫描范围包括消息 JSON、助手与用户头像与背景、收藏快照；草稿与待发送队列还没覆盖，所以真删尚未打开。手动触发是因为全量扫描不便宜，没必要每次启动都跑。

风险同样集中在这里：`Settings.kt`、`SettingsFields.kt`、`SettingsJsonMigrator` 和各设置页是上游改动最频繁的区域之一，拆它会显著抬高合并成本。

建议的时机与追更策略切换对齐：等 `app/` 的改动不再需要逐项对照上游之后，冲突压力本身就小了，那时再动。

## 追更策略

追更仍然要做。完全不跟的 fork 不会稳定在可用状态，它会慢慢烂掉：provider 协议变了、上游 API 挂了、崩溃修不上，最后连打开都用不了。

区别只在于跟什么、怎么跟。

### 模块边界

按模块切分，而不是按 commit 切分。

| 模块 | 性质 | 策略 |
| --- | --- | --- |
| `ai/` | provider SDK、协议适配、模型注册表，与 UI 重构解耦 | 尽量跟随上游 |
| `search/`、`document/`、`common/` | 工具性质的独立模块 | 跟随上游 |
| `terminal/` | 从 termux-app 收进来的终端模拟器核心，与 `workspace/` 配合支持本地与 SSH 终端 | 跟随上游 |
| `workspace/` | 沙箱文件系统与 shell 执行环境 | 跟随上游 |
| `web/` | Ktor 服务端与 web-ui 前端产物 | 跟随上游 |
| `material3/`、`ui/` | 主题工具与不依赖 app 逻辑的 Compose 组件 | 跟随上游 |
| `oauth/` | OAuth 授权与回调处理 | 跟随上游 |
| `app/` | UI、业务、Service，也是大部分定制的所在地 | 我们的地盘。上游的功能性改动逐项评估，bug 修复照跟 |
| `speech/` | C5 删掉了全部运行时实现，只留两个序列化类与它们的序列化测试 | 不跟随 |
| `mediagen/` | C1 保留模块以维持数据兼容，界面不使用 | 跟随，但改到 `MediaGenerationProviderSetting` 这类持久化类型时要复核 |

跟随 `ai/` 时要重放一处定制：C3 删掉了 `ai/util/Request.kt` 里给 aihubmix.com 加 `APP-Code` 请求头的分支。这是 `ai/` 下唯一一处定制，上游改这个文件时要重新删除。

`app/` 的上游功能不整体跟随。但在当前的整分支合并里，一旦在这里出现冲突，不逐行解：以上游版本为基线，重新应用 [`checklist.md`](checklist.md) 登记的内容，顺手删掉不需要的上游新功能。清单里的落点分布：C1 到 C16 除 C3 的 `ai/` 一处、C5 落在 `speech/` 的部分、C13 的根 `build.gradle.kts` 与 `libs.versions.toml` 与 CI workflow 之外，其余都在 `app/`，C4 另有仓库根的三份 README；C17 到 C27 落在 `app/src/main/java/me/rerere/rikkahub/data/`、`app/schemas/` 与 `tools/`。逐行解冲突的成本远高于重放一遍。

取上游版本再重放这套做法只在整分支合并里成立。分层追更落地后不再整体 merge，`app/` 的处置变成：保命层改动手工摘，能力层评估后自己实现，地基层完全不动。两种做法以「是否还在整分支合并」为界，不混用。

上游从 3.0.0 起把多步生成循环放在 `ai/` 里（`ai/src/main/java/me/rerere/ai/agent/AgentLoop.kt`），3.1.1 又把工具执行计时与 models.dev 的模型能力数据放进去。这个划分是否成立可以检验：如果 `ai/` 真的变成了可以独立跟随的干净依赖，说明边界成立；如果没有，就需要重新划分。

### 三层划分

保命层，必跟。provider 适配、上游 API breaking change、崩溃与安全修复。这类通常改动小、集中在 `ai/`，可以直接摘。

能力层，按需移植。上游新增的具体 feature 单独评估后自己实现，不要 cherry-pick，因为它们通常依赖同时期的 app 侧结构，摘过来会拖进来一串前置改动。

地基层，尽量不跟。架构重构、UI 大改。跟一次等于把定制全部重做一遍。上游 3.0.0 的三项重构就是这一类。

### 一次追更的动作

分层追更落地之后按下面的流程走。当前仍是整分支合并，见 [`README.md`](README.md) 的上游同步流程。

1. 扫跟随模块有没有保命层改动：

   ```powershell
   git log --oneline <上次同步点>..upstream/master -- `
     ai/ common/ document/ material3/ mediagen/ terminal/ `
     oauth/ search/ ui/ web/ workspace/
   ```

2. 列 `app/` 区间的提交，逐条标成 要 / 不要 / 以后再看：

   ```powershell
   git log --oneline <上次同步点>..upstream/master -- app/
   ```
3. 保命层直接摘；能力层记进定制清单，评估后自己实现；地基层跳过。
4. 跳过地基层时记下它动过哪些文件。后续保命层的改动很可能落在这批文件上，届时摘取成本会比平时高，需要单独判断，而不是直接 cherry-pick。
5. 跑测试，判据是没有新增失败。

### 定制原则的适用范围

[`README.md`](README.md) 里「改动尽量小，优先断入口」与「避开上游热区」这两条，目的只有一个：让上游的改动能廉价地合并进来。

它们不是本仓库的长期规矩，只是一笔合并成本的对价。等整分支合并结束之后（那时 `app/` 不再需要整体跟随上游），`app/` 里的改动不再需要替上游让路，两条都可以放开：

- 在 `app/` 里，该删的实现直接删掉，不必为了可合并性留一整段死代码
- `ChatVM.kt`、`ChatService.kt` 这类高频文件可以随手改，不必专门绕开

`ai/` 那种仍要尽量跟随上游的模块不在此列，C3 的删除每次合并都要重放，「改动尽量小」在那里仍然划算。

同类的合并成本让步还有几处：把删掉的文件路径记进定制清单以便合并时逐项核对；新定制避开上游重构期；定制清单里那些「刻意保留」的条目，比如 C1 留下未删的实现，留着都是为了不与上游产生 modify/delete 冲突。这些同样只在整分支合并期间必要。

在这之前它们全都有效，因为合并成本是实打实的。

## 分发与合规

独立化有一个决策变量是要不要把这个 fork 分发给别人，它直接影响合规义务。

本仓库是 AGPL-3.0，而项目带 `web` 模块，能在设备上跑 Ktor 对外提供 Web UI。自己构建自己安装不构成分发，没有额外义务。但如果 APK 要分发出去，或者把 web 版挂到公网提供服务，就需要按 AGPL 提供源码。

改包名不改变这一条，它只是让「这是谁的修改版」这个问题变得明确。
